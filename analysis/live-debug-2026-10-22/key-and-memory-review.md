### Captured Bridge timestamp mismatch

A separate 40-repetition original-case diagnostic completed its capture with
29 passes, 11 failures and zero skips; actual pytest exit 1. Capture completion
is not test success. Every failed repetition stopped in the legacy reader with
one protected-store read and no write. Device/inode/size/mtime and birth matched,

remained untruncated/fault-free. Exact native outer retirement and frozen-input

Source review of CPython v3.12.10 confirms that Windows named-path ctime is
CreationTime while descriptor ctime is ChangeTime; the deployed Python DLL's
metadata reports 3.12.10. The captured diagnostic therefore confirms a false-hold
mode. It does not retrospectively establish R4's unrecorded exception cause.

Windows birth across API views; retain full descriptor raw-ctime identity before
and after reading; retain all named-path/store/readback/unlink refusal checks.
The timestamp repair leaves secure-store code unchanged; the broader key
maintenance changes protected-store transactions. Sixteen inert cases across
seven new functions preserve the original test bytes as an exact prefix.
Source approval alone did not constitute a pass; R5 supplies actual results below. No retained-object unlink lease or
administrator/same-user hostile-writer immunity is claimed.
