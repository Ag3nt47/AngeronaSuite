Retained suspended process/Job owners, bounded output, actual root/tree/reader

Failed immediate sends enter a bounded digest. Digest sending reserves its
batch while newer arrivals accumulate separately; failure merges old counts
and samples without erasing new work or renewing response tokens. Existing
signature, receipt, PIN, sender/token and response policy remain required.
Verified local CLI execution is not recipient-delivery proof.

### Later fresh runtime attempt: acceptance held

A subsequent source session reached dashboard readiness, then exited
unexpectedly before the requested combined scans or fresh full drill started.
Bounded Windows Application Error and WER records were correlated to its exact
native process generation. They report an access violation in `python312.dll`
and a later user-callback failure at the same module offset. Current runtime

The first Python diagnostic label carried COM code `0x8001010D`; the OS error
records separately report `0xC0000005` and `0xC000041D`. Microsoft's
[COM code definitions](https://learn.microsoft.com/en-us/windows/win32/com/com-error-codes-3)
and [NTSTATUS definitions](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/shared/ntstatus.h)
identify different conditions. The

- A rare constructor handoff from `os.open` to `os.fdopen` can lose explicit raw
  descriptor cleanup if wrapping fails before the writer stream is assigned.
  This is a low-availability/resource-custody follow-up, separate from the fixed
  AEAD nonce blocker. It grants no response authority and introduces no
  automatic plaintext fallback.
- Live Signal connectivity/recipient delivery and a deployed AMSI provider remain
  unverified. The native compatibility AMSI consumer is not enabled just to
  demonstrate capture wiring.
- The separate VMware source-analysis backend retains its documented native
  configuration-custody acceptance hold. A source copy or parser self-check
  cannot satisfy its VM readiness gate.
- Kernel/PPL/ELAM deployment, PID-birth-bound WFP/ALE admission and complete
  inherited/established socket teardown remain separate acceptance gaps.
  Path firewall evidence is not proof of those properties.
- TPM freshness/counter provisioning and independently administered witness or
  backup authorities require their own deployment and acceptance. Local hashes,
  keys and matching state pairs do not prove whole-root rollback freshness.
- Ring3/user-mode code cannot promise resistance to a fully compromised user,
  administrator, kernel, firmware or hypervisor trust root. DPAPI protects copied
  evidence at rest, not the compromised same-user/kernel context. Host-visible
  peripheral observations cannot exclude invisible cable/firmware implants.
