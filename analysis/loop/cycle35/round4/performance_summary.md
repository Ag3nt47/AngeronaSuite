# Cycle 35, Round 4 — Performance

## Profiled: current Purple Guard marker custody scan

**Component:** `src/angerona/modules/purple_guard.py`, `_validation_target_markers_safe()` via `RedTeamValidationLease._state_matches()`.

**Current-source correction:** `attest_purple_detection()` now checks whether an observed marker is in `state.artifact_handles` **before** calling `_state_matches()`. The 68 orphan markers left by an older failed run are therefore not each triggering a separate full-target validation on every Purple Guard scan cycle. They remain retryable by design. Registered marker attestation, registration, and Combat's begin-handoff still each call `_state_matches()`, which fully revalidates every target marker.

**Measured cost:** A read-only isolated Windows fixture created 0, 20, or 68 inert 600-byte `_redteam_*.txt` files in a temporary target and called the real no-follow open/hash path. Median single-pass time across five repeats was **0.48 / 25.47 / 72.43 ms**. Thirty-seven repeated passes took **21.35 / 896.50 / 2,915.10 ms**, with exactly **0 / 740 / 2,516** marker identity opens. Three such 68-file passes per 37 markers would cost roughly 8.7 seconds on this fixture; actual call counts, filesystem pressure, and cumulative AAR verification can change that. This is a real scaling cost but by itself does not explain the observed 67.871-second serial Combat queue drain.

**Security gate:** `_marker_path_identity()` uses no-follow open, held and pathname identity checks before and after a SHA256 read, regular/single-link/reparse checks, and exact comparison to enrolled content. A cache keyed by name, size, mtime, ctime, or directory metadata can miss a same-stat in-place content rewrite or alias race. Holding handles for up to 4,096 target markers would change Windows sharing semantics and resource use. No behavior-preserving cache or skip was proven, so **no Purple Guard production change was applied**. Existing negative alias/content/race checks must remain mandatory at issuance and handoff.

**Status:** **PROPOSED** only for a future coherent custody design with adversarial equivalence tests.

## Measured: Combat response and durable journal phases

One successful quarantine writes an intent and a commit. Each `_append_journal()` fsyncs the pinned journal, advances and reverifies the recovery anchor and witness, then canonicalizes and MACs the retained record graph. An isolated call to the **actual graph-digest method** over 74 growing synthetic records took **37.78 ms** at 1 KiB per record and **124.69 ms** at 4 KiB per record. This CPU work is minor relative to the observed 67.871-second serial queue drain.

A read-only timing wrapper around **one actual inert-file quarantine** in a Windows temporary root produced two verified quarantines in the same process. The first response took **3.349 s** and included first-use anchor/witness enrollment. The **steady-state second response took 2.308 s**. In that second response, two `_append_journal()` calls totaled **2.231 s**, including two `_advance_recovery_anchor()` calls totaling **1.690 s** and two pinned journal-byte appends totaling **0.505 s**. Six `os.fsync()` calls across the response totaled **1.677 s** (about 73% of wall time; these calls are nested within the phase times). The two protected-map writes totaled **0.731 s**, four `_private_acl()` calls **0.213 s**, two witness writes **0.720 s**, pinned rename **9 ms**, graph digest **1.37 ms**, and `emit()` **0.023 ms**. These are isolated host observations, not production percentile bounds. They show durable writes dominate this fixture. Removing `fsync` or the final ACL pass would alter the rollback or credential boundary and was **not** applied.

A separate two-write real DPAPI secure-store probe on an isolated Windows root measured `write_secret_map()` median **753 ms**. Its `os.fsync()` calls had median **469 ms**, `_private_acl()` median **51.7 ms**, and `os.replace()` median **1.13 ms**. An elevated hardened witness also uses `secure_sensitive_file()`, which may launch further `icacls` processes; the source/test fixture was not elevated. At least two protected-map writes recur per intent/commit response, and each write invokes `_private_acl()` twice. A direct Win32 ACL setter could reduce process launches only after proving equivalent owner, DACL, inheritance, reparse, failure, and final-path checks. This is **PROPOSED**, not applied.

In a retained live GUI journal, 19 quarantine intent-to-commit timestamp gaps had median **1.854 s** (max **3.519 s**), versus **0.393 s** (max **0.564 s**) in an earlier run. Commit-to-next-intent gaps had median **2.576 s** in the slow run. These timestamps are *not* exclusive phase timers: `intent_at` precedes intent append, `committed_at` precedes commit append, and the latter gap includes commit append, event delivery and the next handoff. Shared system load can therefore change the apparent action cost by several-fold. Authenticated process-containment work queued behind file actions is a plausible cause of an expired 30-second test child; Combat queue prioritization is owned by the separate Combat agent.

The source also has a pending exclusive marker handoff race boundary. A targeted Windows fixture held an inert marker through the actual `_PinnedFileMove` share-zero handle: `Path.stat(follow_symlinks=False)` and `lstat()` still succeeded, while `read_bytes()` failed. Current `_validation_target_markers_safe()` uses stat/identity for enrolled exclusive handoffs. The specific hypothesis that the pending marker's `candidate.stat()` must fail with sharing violation was **not reproduced**; no custody check was relaxed. QA's concurrent GUI evidence is still needed to assess other interleavings.

## Bounded GUI mode-transition measurement

An offscreen actual `MainWindow` Chill → Full → Chill heartbeat soak ran in an isolated process after QA's previous GUI process exited. It used one inert module named for the Chill-paused YARA slot and a temporary recorder, so the transition machinery was real but scanner workloads were not. Across **4.493 s** of wall time, the synchronous enter-Chill call took **5.36 ms**, Full wake enqueue took **6.55 ms**, and return-Chill took **10.8 ms**. A 10 ms Qt heartbeat fired 433 times with **40.09 ms** maximum scheduling slip. Process CPU time was **0.469 s** and RSS changed from **88.54 to 92.63 MiB**. The process exited before QA resumed its live GUI test. This fixture neither reproduces a multi-second transition stall nor establishes all-day physical-host behavior or production module load.

The later retained real GUI run under shared system load measured **52.1 s** for `MainWindow` construction and **22.9 s** for Settings Arm/save. These are separate from the inert 4.493-second mode-transition fixture and were not reproduced in isolation. Source inspection shows the constructor synchronously builds host adaptation, dashboard cards, Modules/SOAR/Scan panels, ARIA, Shark/Red Team engines, and tray before the Qt event loop can service a heartbeat. `SettingsDialog` eagerly builds 11 tabs; its Combat tab calls `module.list_actions(limit=100)` synchronously. Its save path synchronously reads protected credentials when touched, checks autostart, writes secrets/settings and explicitly fsyncs settings, applies theme, starts Combat, then calls `list_actions()` again. **PROPOSED read-only probe:** in the next isolated QA child, time each constructor factory and the Settings save call sites with `perf_counter_ns` and thread IDs, plus `cProfile` cumulative time for Python calls, and record Qt timer slip. Split `list_actions()` into journal read and anchor/witness verification. This will distinguish disk/ACL, widget construction, and module startup before changing behavior.
