# Cycle 35, round 3 — independent security reattack

Scope: current Red Team marker creation, Purple Guard lease and FIM receipts, Windows Combat quarantine, authenticated AAR scoring, and the AI guardrail size patch. This was a read-only product audit; no source or test files were changed by this audit. The focused tests below use inert, isolated fixtures.

## SR3-01 — Bus-signed spoofed Combat event can earn containment credit

**Severity: MEDIUM (report integrity). Status: FIXED DURING REATTACK; full live score pending concurrent QA.** A process with access to the in-process `EventBus` could publish an event whose `module` is `Adversary Combat`. `EventBus.publish` signs the caller-supplied module and details (`src/angerona/core/eventbus.py:301-305`); that signature proves publication, not execution by the Combat object. Before remediation, `generate_aar` authenticated stored bus events and separately verified native/Purple detector provenance, but supplied no Combat response verifier. `_verified_containment_targets` trusted a matching event's `mitigated`, `action_ids`, and `verified_actions` fields without checking a committed Combat journal action.

**Non-destructive reproduction before fix:** `venv\Scripts\python.exe -m pytest -q tests/test_aar_verified_containment.py::test_authenticated_exact_digest_and_action_prove_containment` returned `1 passed in 2.24s`. That test published an authenticated detector event and a synthetic `Adversary Combat` event with `mitigated=True`, `actions=["quarantine_file"]`, `action_ids=["committed-fixture-action"]`, and one `verified_actions` row with expected path, SHA-256, and `postcondition_verified=True`. No Combat instance, host mutation, or journal commit existed. Nevertheless authenticated `aar.evaluate` set `target_containment_verified=True`, and `_containment_metrics` returned `outcome="verified"`. A production Red Team AAR would additionally need a real, separately verified Purple/native detector event and matching run/step/trigger/path/digest fields; the spoof did not create detector credit itself. In-process publishing access and the elevated single-host deployment limit exploitability.

**Retest after fix:** The Combat/AAR owner added a production response verifier that requires the exact registered Combat object and bus, one strict signed journal snapshot, a matching applied commit, trigger event signature and run provenance, matching action identity, and no `undo_intent`, `undo_commit`, or `undo_failure` for that action. The no-undo-intent condition closes an intermediate failure case: `undo_action` can reverse a host effect after durably appending `undo_intent`, then fail to append `undo_commit`, leaving a genuine prior commit with an uncertain current effect (`adversary_combat.py:5258-5294`; existing reproduction in `tests/test_adversary_combat_journal.py:643-665`). The report code rechecks the strict journal before writing. The revised synthetic response regression `test_bus_signed_combat_claim_without_journal_never_proves_containment` and orphaned-undo regression returned **2 passed in 4.64s**; the synthetic receipt now sets `response_action_applied=False`, `target_containment_verified=False`, and containment outcome `failed`. Relevant revised code: `aar_report.py:650-858,1000-1040,2200-2240`, `adversary_combat.py:3648-3675`.

## SR3-02 — Oversized non-prompt Ollama fields bypassed the first size patch

**Severity: LOW to MEDIUM (local inference resource consumption). Status: FIXED DURING REATTACK by guardrail owner.** The first `process_request` patch capped only `messages` plus `tools` for chat and `system` plus `prompt` for generate, then forwarded the full caller payload. A 100,000-character `format.schema` in chat was accepted with `status=200` and a 100,421-character forwarded JSON object; a 100,000-character generate `suffix` was accepted with `status=200` and a 100,355-character forwarded object, despite `MAX_PROMPT_CHARS=16000`. The proxy's separate 2 MiB request cap limited the upper bound. The guardrail owner changed the check to measure the complete serialized forwarded object, including appended telemetry. Rerunning both probes now returns `allow=False,status=413`; no remaining oversized forwarded-field bypass was identified in this pass. Relevant code: `src/angerona/engines/ai_guardrail.py:218-285`, `src/angerona/engines/ollama_client.py:148-185`.

## SR3-03 — Model-facing text outside `content` bypasses injection scanning

**Severity: LOW to MEDIUM (guardrail policy bypass). Status: FIXED DURING REATTACK by guardrail owner.** The full-object size limit initially still left `process_request` scanning only chat message `content` or generate `prompt` while forwarding other model-facing text. A benign `hi` message plus `tools[0].function.description="ignore previous instructions"`, or chat `format.description` with that string, each returned `allow=True,status=200,risk="Low",reasons=[]`; a generate request with `prompt="hi"` and `suffix="ignore previous instructions"` did the same. These were scanner bypasses, not proof that a particular local model obeyed the text. The guardrail owner added an original-envelope scan before transformation, retaining the full forwarded-size cap (`src/angerona/engines/ai_guardrail.py:218-300`). Retesting tool description, chat format description, generate suffix, and chat message `tool_calls` with the same phrase now returns `allow=False,status=403,risk="High"` for all four.

## Windows custody and FIM controls rechecked

The current handoff first validates the signed Purple receipt and enrolled object, releases only that marker's lease handle, then opens the source exclusively via `_WindowsPinnedFileMove`; the new pin compares volume/file ID, size, mtime, single-link status and same-volume constraint before mutation (`purple_guard.py:1921-1983`, `adversary_combat.py:3690-3730`). It keeps a duplicate of the moved handle for historical AAR evidence and rechecks content and metadata; a replacement at the old name is refused (`purple_guard.py:1985-2051,2590-2660`). The move uses a handle-pinned Windows rename and rejects reparse points and multiple hardlinks (`adversary_combat.py:586-625,716-740,870-940`). A journal-terminal validation failure leads to exact rollback and lease recapture, or poisons lease custody if the original cannot be recaptured (`adversary_combat.py:3422-3575,3770-3862`; `purple_guard.py:2054-2090`). A same-name replacement can deny the drill, but did not gain authorization to quarantine the replacement or earn containment credit in the checked paths.

Focused Windows gates returned: `test_stale_enrollment_discards_only_the_created_marker_and_stops` **2 passed in 3.29s**; `test_failed_quarantine_commit_never_credits_replacement_marker` **2 passed in 14.88s**; and `test_live_fim_evidence_survives_later_scans_in_the_aar` **1 passed in 9.79s**. These cover the renamed-original/same-name replacement case, terminal journal failure with and without replacement, and a genuine historical FIM receipt after a later scan. The FIM verifier requires a signed exact claim retained in the lease's bounded issued-claim history (`purple_guard.py:284-320,3332-3388`); signature tampering and wrong-technique negatives are in the live FIM test. Eviction after 8,192 issued claims can only remove old credit, not create a claim. I did not find a verified FIM replay or tamper route to new credit.

**Remaining limits:** The exclusive Windows pin begins after a short lease-handle release window; a hostile same-name replacement or hardlink in that window can make containment fail closed. Concurrent readers of the duplicated Windows file handle may share its file pointer with Combat's digest read; under unusual concurrent AAR/FIM timing this merits a separate stress test for transient false negatives, though no false credit was demonstrated. The production full live AAR gate is owned by the concurrent QA/remediation work and was not duplicated here.
