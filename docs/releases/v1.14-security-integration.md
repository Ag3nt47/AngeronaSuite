All nine requested protection upgrades belong to **v1.14**. This is the current
development and acceptance register. An item being in scope does not establish
that its enforcement backend is deployed or that its acceptance test has passed.
Publication follows the observation, remediation and validation gates below.

## Readiness evidence

Collection uses exact registered built-in objects, current lifecycle generation,
completed work, health of at least 90 and no known or unknown overflow. Its
age limit is `max(30, min(3600, 3 * cadence + 5))` seconds. Scoped detection
proof expires after 24 hours; response proof expires after one hour. A stopped
or replaced producer invalidates its readiness immediately. Generic canary
observations do not automatically qualify as technique-specific tests.
Clock rollback cannot revive an earlier proof after the clock recovers. Typed
Process Monitor denial/partial/error receipts withhold collection credit; a
complete receipt remains eligible.

Readiness is an advisory presentation cache. It does not acquire the original
receipt's single-use response authority or create a second response path.
The dashboard's tested coverage percentage is separate from its declaration
count. A fresh installation with stopped sensors can correctly show zero
verified coverage even though many detector mappings exist.

## Independent custody

The witness must run under separate administration with separately provisioned
host and witness Ed25519 roles, private mTLS certificates and an exact fixed
vault enrollment. Its first initialization is explicit and create-only; normal
startup requires both the authenticated enrollment marker and retained state.
There is no remote reset, arbitrary signing or command-execution endpoint.
The private-PKI/mTLS URL ends in `/v1/ugcap-witness` and enrollment requires an
exact TLS leaf-certificate pin and witness Ed25519 public PEM. Intentional
vault/baseline identity changes require independently reviewed witness
enrollment or reconciliation. Disabling a required witness, deleting state or
resetting the retained head cannot satisfy that review.
Applying settings clears the old checkpoint/receipt. A fresh full UGCAP
**Verify now** with the enrolled vault, passcode and required TPM-backed
hardware proof creates the current
checkpoint. **Check witness now** only heartbeats an already verified checkpoint;
it cannot enroll or reset the remote head on its own.

Only public vault identity, baseline identity, chain length/hash and at most
128 authenticated anchors are sent. Passcodes, decrypted vault contents and
source-file paths do not become witness payloads. More than 128 unwitnessed
steps can require reconciliation; that gap cannot be treated as a clean match.
No real off-host destination is configured by this development update.

The current diagnostic response service accepts only status, operator-proof
verification and candidate inspection. It does not expose a privileged mutation
dispatcher. The Windows Prevention backend is composable behind the existing
capability-consuming service contract, but no source-mode guard, caller-supplied
flag or public diagnostic request can install that authority.

Native process-bound connection admission remains **not implemented and not
validated**. The local feasibility review found incomplete compiler/SDK headers
and libraries, no usable driver build/signing acceptance environment, and a
missing project file referenced by the existing sensor build script. No driver,
filter or certificate was installed. Acceptance must include process-held
identity, replacement/reuse and lease-expiry cases for IPv4/IPv6 TCP and UDP.
Microsoft's [ALE layer contract](https://learn.microsoft.com/en-us/windows/win32/fwp/ale-layers)
places outbound admission at AUTH_CONNECT and identifies FLOW_ESTABLISHED as
post-admission; a later connection snapshot cannot prove that admission was
enforced.

The same separation principle applies to backups and release signing: a local
signed statement does not prove physical independence, and repository automation
must not acquire release-authority private keys. See the
[release signing boundary](../enterprise/RELEASE_SIGNING_BOUNDARY.md).

Recovery needs a running Immutable Recovery Assurance Guard and no UGCAP
workspace hold. Enroll the independently trusted 32-byte Ed25519 recovery
public key as base64, then select the local ciphertext and signed statement.
The original 32-byte encryption/audit keys or existing protected OS-store keys
are required; replacements are never generated and one-shot keys are never
retained for recurrence. Up to 16 private plaintext test directories remain for
fresh rechecks, with operator review at capacity and no automatic deletion.
Opt-in recurrence is 1–720 hours with reusable protected keys and is disabled
when the worker/process stops. See the [workflow guide](../live-debug-harness.md#witness-and-independent-recovery).

## Reproducible replay checks

From the source checkout, run:

```powershell
venv/Scripts/python.exe tools/evaluate_detections.py `
  --active examples/cohorts/active.json `
  --candidate examples/cohorts/candidate.json `
  --cohort examples/cohorts/labelled.json `
  --training-cohort examples/cohorts/training.json `
  --output .tmp/heldout-comparison.json
```

This authored synthetic example reports **2 true positives, 1 false positive,
2 false negatives and 3 true negatives** for the candidate. It demonstrates
honest accounting, not product efficacy against real attacks. The report binds
evaluation/training source digests and package digests. Exact event content is
compared independently of record IDs, revisions and labels. Prior exposure,
undeclared training sets, semantically equivalent events and independent label
review remain unproven. Incomplete cohorts cannot receive holdout credit.

## Current observation and release gates

The October 22 investigation includes actual ordinary-user desktop and Black
Box observations, native pipe/Qt shutdown tests, isolated scanner/control
processes, read-only host probes, offline module self-tests and adversarial
fixtures. Captures containing host information stay private. The public
[issue register](../../analysis/live-debug-2026-10-22/README.md) records causes,
fixes and unresolved observations without publishing those captures.

The latest completed selfcheck passed 29 phases, accounted for all 86 built-in
modules and exited normally. It predates the final small source changes and
requires a fresh run after the frozen-tree full suite. Identity collection encountered denied access to
the Windows Security channel under this account and retained that gap; it did
not elevate or modify audit policy. The browser probe produced manifest
metadata only. These results do not establish administrator- or kernel-resistant
protection on this host.

The earlier broad run's **5,991 passes / 5 failures / 32 skips** is retained as
historical evidence because the source changed during that run. Exact-node
follow-up passes do not make it a stable-tree suite. The 1,159-input frozen-tree
full run was aborted after a legacy recovery fixture did not terminate; its
partial progress and inline failures do not form a full-suite result. A
corrected-fixture stable-tree rerun is pending. The 15 individual/scanner
observations continue; they overlapped full regression, so concurrent host
contention is part of their recorded scope. Focused groups are not additive.

Final acceptance requires a stable reviewed tree, repeatable per-module and
combined observations, relevant complete offline validation, reviewed artifacts
and the guarded GitHub publication proof. Unprovisioned independent authorities
must remain visible; neither a successful source test nor a version label may
silently satisfy them.

## Current dependency and local-service fixes

The dependency locks now require certifi **2026.10.19** and bootstrap pip
**26.2.2**, including the latter's corrected vendored CA bundle. Reviewed wheel
hashes remain pinned across supported release locks. The fresh installed
environment audit reports no known vulnerabilities; local source-package skips
remain explicit in its evidence. See the
[certifi advisory](https://github.com/advisories/GHSA-6q48-6c7w-9gw2) and
[pip release notes](https://pip.pypa.io/en/stable/news/#v26-2-2).

An actual wildcard Ollama listener was rejected, then restricted to this
computer with explicit operator authorization. A GPU-discovery compatibility
setting restored its API while preserving CUDA discovery. Angerona forwards
only a strict boolean `OLLAMA_VULKAN` override; arbitrary library paths, proxy
settings, cloud-policy overrides and wildcard host settings remain excluded
from its sealed launch environment. See Ollama's
[backend troubleshooting](https://github.com/ollama/ollama/blob/main/docs/troubleshooting.mdx)
and [backend configuration](https://github.com/ollama/ollama/blob/main/envconfig/config.go).
