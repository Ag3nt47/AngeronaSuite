# Angerona 1.15.1 security maintenance

This maintenance update applies the reviewed security worklist to the PC source
checkout and keeps GitHub publication tied to that exact reviewed local commit.
It remains a user-mode source preview. The
[29-item review](security-worklist-review-2026-11-13.md) distinguishes tested
fixes, partial mitigations, deliberate capability holds and remaining exposure.

## Third watchdog modes

The native Go helper can be bundled unsigned. Its optional ordinary-user monitor
is **off by default** in Settings > Watchdog. When enabled and its actual
generation supplies fresh advancing evidence, the display says
**Active · Unsigned · Reduced protection** when the image is confirmed unsigned,
or **Active · Signature unverified · Reduced protection** when verification is
unavailable. A verified signed image can also run in this same reduced observer
mode; its label is **Active · Reduced protection**, with a separate green
signature marker. Missing or stale evidence never earns an active label. This
mode supplies no privileged service, firewall or containment authority and is
easier to terminate or tamper with than an independently protected service.
The current unsigned monitor shares the Core's user-session/job lifetime and
reports independent recovery unavailable. It cannot promise to restart a Core
that closes that shared job. This recovery limit is displayed separately from
its real monitoring heartbeat.

Installed protected supervision requires the watchdog's own verified signature,
an explicit protected enrollment binding its final bytes and certificate, and
the existing engine, service, configuration and STOP checks. Signing alone does
not activate it. The unsigned bundled artifact is not silently enrolled and
the source application does not create a certificate, trust root or service.

The third-watchdog heartbeat has a separate signature marker. A green check
means a verified signature for that exact admitted helper image. A red cross
means unsigned or unverified metadata; its tooltip distinguishes those states.
The EKG independently shows liveness, so a signed but stale helper still
flatlines. Cached signing metadata is bounded to the admitted live generation,
a 15-minute review window and certificate expiry; outside that scope it becomes
unverified. Click the marker to open Watchdog signing settings.

A [synthetic screenshot of the actual controls](../../assets/screenshots/watchdog-signing-demo.png) shows the separate heartbeat, unsigned warning and signing-review controls. It contains no host data.

## Signing updates

Settings > Watchdog provides current signature, signer, certificate fingerprint
and expiry information when verified. Select a newly signed watchdog3.exe and
choose **Verify selected signature**. The reviewed bundled inspector opens that
file as data; it never executes the selected candidate. Missing inspector or
unavailable verification remains visible.

**Prepare signing update** creates explicitly untrusted planning data.
**Export update request** writes a separate review report, preserving existing
files. A separately governed signed installer must reverify the final deployed
bytes, publisher, protected destination and existing service authority before
applying enrollment. Source settings never elevate mutable code, import trust
roots, manufacture signing authority or claim activation from a prepared request.
See the [Windows service and signing guide](../enterprise/WINDOWS_SERVICE_ONBOARDING.md).

## Native custody and source-input limits

Uncertain native handle or WinTrust-provider cleanup creates a sticky custody
hold. The verifier retains the exact input owners and file handles, does not
retry an uncertain close or reuse that provider state, and refuses later native
admission in that process. A visible hold is safer than claiming that an
unverified native operation finished successfully.

The ordinary-user source observer streams its directory inventory and limits
it to 256 entries, at most 128 recorded source inputs, 2 MiB per source file and
a 32 MiB helper image. Admission checks a five-second budget between steps;
this is not a guarantee that a blocked operating-system call can be cancelled
at that deadline. A missing build record, changed input, oversized tree or
exceeded budget holds only this optional helper. The application and its
available diagnostics can remain usable. No automatic rebuild, download,
trust import or privilege escalation follows from that hold.

## Security and reliability changes

- Recovery manifest, verifier, application profile and four launcher pins are
  checked together. Normal source startup uses a fresh private bytecode path.
- Source archives must match reconstructed Git tree objects and their exact
  member/blob inventory. Managed source lineage holds automatic historical
  rollback. Canonical GitHub remains a supplier trust boundary.
- Local control and restart admission, bounded corrupt-state recovery,
  ring cursors and publish-before-ACK peer delivery have stricter contracts.
- IPC uses mutual role-bound admission. Mobile PIN attempts have persistent
  limits and consume one-time material before comparison. Mail uses verified
  TLS and advisory deduplicated observations.
- Exact expiring acknowledgements replace broad legacy suppression. Reviewed
  model/feed text renders literally. Memory classification retains raw flags
  while recognizing executable-writable base protection with Windows modifiers.
- Unsafe POSIX binary installation, new Windows legacy deception writes and
  the defective dormant syscall-bridge build paths are held before effects.
  These holds preserve the dashboard and reviewed alternative scopes while
  making unavailable protection explicit.

## Final reliability and self-test explanations

The optional monitor waits for a single-use admission event before native work.
Admission is released only after Thread.start returns successfully. An uncertain
worker start leaves that optional owner under a sticky hold while the Core's
other workers continue.

Scanner GUI shutdown is queued only after authenticated STOP and successful
cleanup. Maintenance ownership parsing accepts at most 16 harmless Python
prefix switches before the known entry point; -c commands and unknown entries
cannot masquerade as an owned Angerona worker.

The AI provider self-test now explains the difference between availability and
verified write custody of a per-machine installation. Unverified required
custody still produces FAIL. A separate read-only host assessment confirmed
that this protection was unverified. It assessed custody only, made no verdict
on the presence or absence of malware/compromise, and changed no provider ACLs.

## Native atomic write reliability

Windows private-file updates now include an explicit UTF-16 terminator inside
the rename buffer while keeping the counted filename length unchanged. A
bounded native comparison reproduced 16 invalid-name failures with the old
encoding and 16 successes with the terminated form. Path validation, private
ACLs, retained file handles and atomic publication remain required.

Private-write diagnostics add a fixed operation label and preserve the original
operating-system error identity. The new label adds no host paths; underlying
error details still require private handling. Native compiler
discovery selects one application path before assigning it to a string.
These changes do not sign, enroll or activate the optional watchdog.

## Scheduled task alert repetition

Persistence comparison now ignores only Ready, Running and Queued transitions
when a complete, strictly typed selected collector record has no other changes.
All collected action, principal, trigger, settings, author and description
changes retain normal detection. Disabled or unknown states, additions and
deletions remain visible. This compares the selected fields, not every possible
property of the full Windows task XML.

Raw snapshots, existing baselines and prior alerts are preserved. Ambiguous,
duplicate, oversized, malformed or depth-truncated records receive no runtime state equivalence. A failed scheduled-task collection stays unknown while
other persistence surfaces continue. No application-name exception or new
response authority was introduced.

The focused comparison, real run-loop, baseline-disposition and startup-hash
cohort passed 164 cases using private test profiles and verified source origins.
A live review candidate had truncated old/current values, so this fix does not
declare that particular event harmless or resolve its original evidence.

The module’s own synthetic Self-Test also checks state-only noise, changed
execution and disabled-state drift. Fault injection verifies that both noise
regressions and overbroad suppression make it fail. It does not claim host
collection. A separate actual read-only collector smoke check completed; it
changed no tasks, baselines, alerts or settings.

## Validation and remaining limits

Dated offline records retain their exact tested source and retirement scope.
The initial worklist candidate's accepted checks do not automatically validate
this combined revision or a different process generation. Publication requires
fresh relevant checks and guarded exact-commit/default-main and asset proofs.

Accepted maintenance scopes include 146 watchdog/settings checks, 119
supervision checks, 129 provider-explanation/admission checks and 52 service
checks with one skip. Peer STOP passed 12 pytest checks, including a PowerShell
fixture with 48 supplied rows. Heartbeat/native leases passed 45 checks with
one skip, plus one separately accepted reparse case. The native suite passed
93 top-level tests with one export-only skip; full go vet exited 0. These
scopes overlap and are not a unique suite total.

A confined ordinary-user Go observer produced two authenticated advancing
progress frames with verified exact-image pin, Job ownership and Popen
retirement. Its Core endpoint was diagnostic only. Actual unsigned-file
inspection passed; a valid --validate-only request stayed inactive with exit 5.
These checks do not establish protection of the actual Core or a signed
operational launch. See the [sanitized scoped acceptance record](../../analysis/maintenance-v1.15.1-acceptance-2026-11-13.md).

Final syntax, full selfcheck, provider-hold reconciliation, interoperability,
publication and fresh hosted results remain separate acceptance records.

A real successfully signed, protected and enrolled watchdog has not yet passed
a positive deployment exercise in this review. Inert signer fixtures, a
passing unsigned test image and read-only unsigned inspection do not establish
that positive case. Trusted publisher signing, machine-chain acceptance and
signed clean-VM installation/recovery remain separate work.

An administrative STOP namespace whose ownership or replacement rights cannot be verified remains held. It is never silently reset or downgraded to a user-key fallback. Maintenance of known ordinary-user source processes does not establish protected STOP authority.

Same-user source/key compromise, whole-root rollback, compromised administrator
or kernel, unresolved optional native driver defects and the Source Observe
network-enforcement gap remain explicit. A green signature marker, responding
heartbeat, empty finding list or completed workflow does not prove complete
sensor coverage or a clean PC.
