# Third watchdog (Go) — original outline and implementation status

**Implementation: [`watchdog3/`](watchdog3/README.md), added 2026-11-13.**
The new component is a standalone Windows Go executable. Development builds
are unsigned and are not auto-started or registered on the host. Production
deployment still requires the protected publisher and installer; building is
not evidence of installation or active recovery. The following sections retain
the original design outline. Current build and behavior details are in its README.

The installed implementation uses the approved native SCM service route. The
current service graph does not publish the original Python pair's heartbeats;
the native supervisor does not fabricate them or bypass package/UAC admission
with a direct `--chill` launch. A clean SCM stop remains stopped. The heartbeat
and pair-policy sections below are historical design/protocol material, not a
claim that the installed service has that deployment shape.

Recorded 2026-11-12. The ranked attack-path analysis behind it is a local-only
file that is not published; ask the operator for it before building this.

## Why a third supervisor

Today the only supervision that actually runs is the Python pair: the core's
`ResilienceManager` and the peer watchdog (`resilience/watchdog.py`). Both are
Python, both run as the same user, and ending both together leaves nothing to
bring protection back until the next logon. The existing Go parent in this
folder (`angerona_watchdog.go`) is designed but has never been built or signed,
and its liveness and clean-exit logic must not be reused (see "Do not reuse").

The third watchdog is a small native process, outside the Python runtime, that
watches **both** Python peers and brings the suite back when both are gone.

## Boundary (unchanged from `angerona_watchdog.go`)

It is a **plain, bounded supervisor**, deliberately not un-killable:

- It honours STOP. An operator stand-down ends supervision without a fight.
- It does not resist termination by its owner or an administrator, hide
  itself, or install persistence of its own. Start-up is whatever the signed
  installer registers (service or scheduled task), nothing else.
- It has no response authority: it never terminates, blocks or quarantines
  anything other than relaunching Angerona's own peers.
- A watchdog that fought its own owner would be indistinguishable from the
  malware it exists to catch. That boundary is the design, not a limitation.

Durable protection against same-user termination comes from the signed,
elevated install (service account, process DACL, SCM recovery), not from
tricks in this process.

## Responsibilities

1. **Observe** the `core` and `watchdog` heartbeats (authenticated v2 records).
2. **Decide** liveness per peer: alive, suspended (PID present, counter
   frozen), dead, or unauthenticated.
3. **Honour STOP** before every relaunch decision (see "STOP").
4. **Relaunch** only when *both* Python peers are down past a grace period;
   while either peer is alive, that peer owns recovery of the other.
5. **Report** every decision as an authenticated alert the core ingests.
6. **Publish its own heartbeat** so the core can show it and alert on its loss.

## Inputs it reads

| Input | Location | Format |
| --- | --- | --- |
| Peer heartbeats | `<data>/heartbeats/core.hb`, `watchdog.hb` | 32-byte little-endian record, `resilience/heartbeat.py` |
| Install authority | `<data>/shutdown.key` | 32 raw bytes, hex text; ACL-protected |
| Admin STOP (when provisioned) | `<ProgramData>\Angerona\control\{stop-authority.pub, epoch.json, stop.cmd}` | Ed25519-signed JSON, `resilience/control_authority.py` |
| Legacy STOP (unprovisioned hosts) | `<data>/ipc/standdown.cmd` | HMAC-signed JSON, `resilience/shutdown_token.py` |
| Launch command | fixed at install time | never from the environment |

Heartbeat record (v2): `magic u32 "AWDG"`, `ts_ns u64`, `pid u32`, `proof u64`,
`count u32`, `flags u32` (bit 31 = v2-authenticated, bit 0 = running).
`proof` is the first 8 bytes of `HMAC-SHA256(component_key, len(name) u16 ||
name || ts_ns u64 || pid u32 || count u32 || flags u32)` where
`component_key = HMAC-SHA256(install_authority, "angerona-resilience-heartbeat-v2\0" || name)`.
Reimplement these from `heartbeat.py` and pin them with shared test vectors
generated by the Python side; do not copy constants by eye.

## Liveness rules

- **Authenticated or nothing.** A record that fails its proof is
  "unauthenticated", never "alive" and never "clean exit".
- **Alive:** proof verifies, `pid` exists, and `count` advanced within the
  stale threshold (core 12 s, watchdog 10 s — keep in step with the Python
  constants).
- **Suspended:** proof verifies and `pid` exists but `count` has not advanced.
- **Dead:** `pid` gone, or record missing after the start-up grace (180 s).
- **Clean exit** is only ever a verified STOP, never a flag in the record.
- Bind to the process, not the number: record the peer's creation time when
  first seen and treat a PID with a different creation time as a new process.

## STOP

Check in this order before any relaunch and on every loop:

1. If the admin control directory is provisioned, STOP is active only when
   `stop.cmd` verifies under `stop-authority.pub`, matches the current signed
   epoch, and (for maintenance) has not expired. The legacy command is then
   ignored entirely.
2. Otherwise the legacy `standdown.cmd` verified with the install authority.
3. If the control directory exists but does not verify, treat STOP as **not**
   active and raise an alert: tampering must never become a stand-down.

While STOP is active the watchdog relaunches nothing and stays idle (or exits
cleanly, as the installer's registration prefers). It never clears STOP.

## Relaunch policy

- Trigger: both peers not alive for a continuous grace window (suggest 20 s),
  and no STOP.
- Action: start the pinned launch command once, in recovery (`--chill`) mode,
  with a sanitized environment built from an allow-list. Verify the launcher's
  digest against an install-time pin first; on mismatch, do not launch, alert.
- Pace: exponential backoff from 1 s to 60 s between attempts.
- **No permanent give-up.** A restart storm slows attempts to the 60 s
  ceiling and raises a Critical alert; it never ends supervision for the
  session.
- Restart pressure accounting mirrors `supervisor.py`: count unexpected stops
  over 10 minutes, 1 hour and 24 hours and escalate elevated/attack.
- Single instance: a named mutex (Windows) or lock file; a second copy exits.
- Use the shared spawn lock (`<data>/ipc/*.spawnlock`) so it never
  double-starts a peer the Python pair is already starting.

## Outputs

- **Alerts:** append to its own HMAC-chained file in the
  `resilience/peer_alerts.py` record format (one writer per chain). The core
  would add one more `PeerAlertReader` for it, as it has for the crash hunter.
  Alert text carries counts and states only, never attacker-influenced strings.
- **Heartbeat:** `<data>/heartbeats/watchdog3.hb`, same v2 record, so the core
  manager can supervise it and the status views can show it.
- **Status:** `status_watchdog3.json` through the same shape as
  `diagnostics.write_status`.
- **Log:** bounded, rotating, in the private diagnostics directory.

## Standard process hygiene (not anti-termination)

- Static build, no runtime dependencies: `go build -trimpath -ldflags="-s -w"`.
- Signature-enforcement and extension-point mitigation policies, as
  `hardenSelf()` already does in `angerona_watchdog.go`.
- Private ACL on its data files; fail closed on unreadable authority.
- No network sockets, no command-line secrets, no shell invocation.
- Bounded reads everywhere; every file it parses has a maximum size.

## Do not reuse from the existing Go parent

Write the liveness, clean-exit, launcher-digest and restart-storm logic fresh
from this outline rather than copying `angerona_watchdog.go`. The specific
findings against that file are in the operator's local analysis. In short:
authenticate every record, treat only a verified STOP as a clean exit, pin the
launcher digest at install time, match the Python record size, use the path
`resilience/manager.py` looks for, and never give up for the session.

## Build, sign, ship

- Source layout: `frz/watchdog3/` with its own `go.mod`; unit tests beside it.
- CI: extend the existing "Native watchdog console and STOP contracts" job to
  build it and run its tests with inert helper processes.
- Release: build in `release.yml`, sign with the publisher certificate, and
  pin its SHA-256 the same way `frz_watchdog_v2.exe` is pinned
  (`FRZ_WATCHDOG_SHA256`). Unsigned or unpinned binaries are never launched by
  the Python side.
- Registration: the signed installer registers start-up. Source runs do not
  auto-start it.

## Tests required before it may be called present

- Shared heartbeat test vectors (Python writes, Go verifies, and the reverse).
- Forged, replayed, truncated and wrong-component records are never "alive".
- STOP: admin-signed, legacy, expired maintenance, stale epoch, tampered
  control directory.
- Both-dead relaunch, single-dead no-op, suspended peer, PID reuse.
- Restart storm keeps supervising and escalates; backoff stays bounded.
- Launcher digest mismatch refuses to launch.
- Second instance exits; spawn lock respected.
- Alert chain verifies with `PeerAlertReader`; edited lines are reported.
